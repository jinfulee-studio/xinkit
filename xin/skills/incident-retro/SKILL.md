name: incident-retro
description: Structured incident retrospective — classify, find the real root cause with 5-Why, extract the pattern, produce four artifacts (rule / detector / blindspot entry / ledger row), verify. Use after any incident worth not repeating.
---

## 定位

将"事故发生"到"防错表条目+自动检测脚本"的完整流程标准化，确保每次事故都变成可复用的知识资产。
不是事后追责工具，而是** 复利的加速引擎**：每个事故 → 1 个防错条目 + 1 个检测脚本 + 1 条盲区预检 + 1 条复盘记录。

## 触发方式

```
/retro
```

然后提供事故描述（口述、错误日志、截图均可）。

---

## 执行流程（5 阶段，串行）

### Stage 1 — 事故分类

对输入进行三维分类，输出分类结论：

**严重度**：
- 🔴 P0：线上事故 / 数据丢失 / 服务中断 / 安全泄露
- 🟡 P1：系统性缺陷 / 静默失败 / 评分失真 / 多处同模式错误
- 🟢 P2：最佳实践违反 / 代码质量问题 / 边界未覆盖

**领域**（选一个或多个）：
`Shell` / `TypeScript` / `Python` / `Config` / `Security` / `Infra` / `DB` / `API` / `UI` / `Agent-Arch`

**影响范围**：
- 单文件：仅影响 1 个脚本/文件
- 单项目：影响 1 个项目内的多个文件
- 跨项目：影响多个项目（如全局 hook、CLAUDE.md 规则）
- 全局：影响整个  生态

**Gate 1**：严重度已分类（P0/P1/P2） ∧ 领域已标注（至少 1 个） ∧ 影响范围已确定（单文件/单项目/跨项目/全局）

---

### Stage 2 — 根因分析（5-Why 自动执行）

从事故现象逐层追问，定位根因：

```
现象：{事故描述}
Why 1：为什么会发生？→ {直接原因}
Why 2：为什么{直接原因}？→ {间接原因}
Why 3：为什么{间接原因}？→ {深层原因}
Why 4：为什么{深层原因}？→ {根本原因}
Why 5（可选）：为什么{根本原因}？→ {结构性原因}

根因层级（代码/配置/流程/认知）：{层级}
根因：{一句话描述，≤20字}
```

**Gate 2**：5-Why 链完整（≥3 层，≤5 层） ∧ 根因层级已分类（代码/配置/流程/认知） ∧ 根因描述 ≤20 字

**根因层级说明**：
- 代码：实现逻辑错误（边界未处理、类型错误、竞态条件）
- 配置：配置值错误（单位混淆、路径幻觉、格式不匹配）
- 流程：步骤缺失（未验证、未扫描同类、未写防线）
- 认知：认知偏差（误解 API 语义、误信文档描述、盲目自信）

---

### Stage 3 — 模式提取

从根因提取可复用的防错规则，格式严格对齐 规则文件：

```
{emoji}{级别} {领域}：{规则描述}
```

**格式规范**：
- emoji 对应级别：🔴=P0（线上事故） / 🟡=P1（系统性缺陷） / 🟢=P2（最佳实践）
- 领域首字母大写（macOS 兼容 / Hook timeout 单位 / JSONL 输出格式 等）
- 规则描述：`{禁止做什么}（{原因}）。{正确做法}`
- 末尾建议附：`{年月日 PX 事故：{一句话根因描述}}`

**示例**：
```
🔴 macOS 兼容：Shell 脚本禁止直接使用 timeout（GNU coreutils，macOS 不存在）。
用三级 fallback：gtimeout（brew）→ timeout（Linux）→ perl -e 'alarm N; exec @ARGV'。
```

**Gate 3**：防错规则已提取 ∧ 格式对齐（emoji + 级别 + 领域 + 规则描述 + 正确做法） ∧ 可直接插入 规则文件

---

### Stage 4 — 四项产出（必须全部完成）

一次复盘只有产出了这四项才算闭环。少任何一项，下次同类事故照样发生。

| # | 产出 | 落在哪 | 要点 |
|---|------|--------|------|
| 4.1 | **规则条目** | 你的常驻规则文件（CLAUDE.md / AGENTS.md / 团队规范） | 按严重度排序插入，P0 不能插到 P1 之后 |
| 4.2 | **检测脚本** | 项目的检查脚本目录 | 能自动扫出同类模式；写完先用坏样本验它会红 |
| 4.3 | **盲区清单** | 动手前会被读到的预检清单 | 归入已有模式类，或新建一类 |
| 4.4 | **复盘台账** | 一行 JSONL，可累积可统计 | 单行紧凑格式，便于日后 grep 与聚合 |

**Gate 4**：四项全部落盘才能进 Stage 5。「等下再补」= 不会补。

#### 4.1 规则条目的写法

严重度分级：**P0** 线上事故驱动 / **P1** 系统性缺陷 / **P2** 最佳实践。

一条合格的规则包含：**触发条件**（什么情况下适用）+ **禁止或要求什么**（可执行的动作）+ **判据**（怎么知道违反了）+ **防线**（谁来自动检查）。

只写「要小心 X」不算规则——它没有触发条件，也没人能验证你有没有遵守。

#### 4.2 检测脚本的最低要求

- 能在全代码库扫出同类模式，不是只检查出事的那个文件
- **必须先用坏样本验证它会红**：故意造一个违规样本，确认脚本报警。没验过的检测脚本等于没有
- 白样本免误杀：非目标样本静默通过，否则告警疲劳会让人关掉它

#### 4.3 盲区清单

盲区不是「我不知道的事」，是「我以为我知道但其实错了的事」。每条盲区记录：**当时的错误假设** + **真实情况** + **下次动手前该问的那个问题**。

#### 4.4 复盘台账

一行 JSON，字段建议：时间、严重度、领域、根因类型、模式描述、检测脚本名、影响范围。

累积到一定量后能回答一个别的方式回答不了的问题：**我反复栽在哪一类事情上。**

### Stage 5 — 验证（三项必须全部通过）

1. **脚本语法验证**：新检测脚本 `bash -n` 通过（exit 0）
2. **防错表条目验证**：Grep CLAUDE.md 确认新条目已存在（关键词命中）
3. **格式验证**：新条目以 `🔴`/`🟡`/`🟢` 开头，含 P0/P1/P2 标注

**Gate 5**：脚本语法验证通过（bash -n exit 0） ∧ 防错表条目已存在于 CLAUDE.md（Grep 命中） ∧ 条目格式合规（emoji + 级别标注）

验证后输出摘要：
```
[/retro 完成]
严重度：{P0|P1|P2} | 领域：{领域} | 影响：{范围}
根因：{一句话}
防错表：CLAUDE.md +1 条（{emoji}{级别} {领域前缀}）
检测脚本：检测脚本（bash -n 通过）
盲区预检：{模式类} 已更新 / 新建{模式类}
复盘记录：复盘台账 +1 行
```

## 抑制条件

| 用户说 | 执行 |
|--------|------|
| 默认（无特殊说明） | 全部 5 步 + 4 项产出 |
| "只记录不修" | Step 1-3 + Step 4.4（仅 JSONL 记录），跳过 4.1-4.3 |
| "只分析" | Step 1-2，输出根因分析，不写任何文件 |
| "快速模式" | Step 1-3 + 4.1 + 4.4，跳过 4.2（检测脚本） |

## 使用示例

### 示例 1：macOS timeout 事故

```
用户：/retro
脚本在 macOS 上 timeout 命令不存在导致静默失败

[Step 1] P0 | Shell | 跨项目
[Step 2] 根因：macOS 无 GNU timeout，脚本假设 Linux 环境
[Step 3] 🔴 macOS 兼容：Shell 脚本禁止直接使用 timeout...
[Step 4]
  4.1 → 规则文件 +1 条
  4.2 → retro-check-macos-timeout.sh（grep 全目录 `timeout [0-9]` 未用 gtimeout 的实例）
  4.3 → 盲区清单 B 类新增历史案例
  4.4 → 复盘台账 +1 行
[Step 5] 验证通过
```

### 示例 2：JSONL 多行写入事故

```
用户：/retro
jq -n 写 JSONL 导致多行输出，tail -1 读到不完整 JSON

[Step 1] P1 | Infra | 跨项目
[Step 2] 根因：认知 — 误以为 jq -n 输出单行
[Step 3] 🟡 JSONL 输出格式：写入 .jsonl 的 jq 命令必须用 -c 标志...
[Step 4]
  4.2 → retro-check-jq-compact.sh（grep 全目录 jq 写 .jsonl 时无 -c 的实例）
  ...
```
