## 6. 根因图与高杠杆机会

用最短因果链把多个症状归并：

```text
品牌/内容真相缺失
→ 页面命题不清
→ Hero、导航与动效各说各话
→ Design / Creativity / Content 同时受损
```

每个根因说明：

- 它解释了哪些 finding；
- 先修它能删除或简化哪些下游工作；
- 哪些现象仍需独立处理；
- 需要谁批准方向。

## 7. 双轨优化方案

### Track A — Stabilize

按依赖排序处理：

1. P0 阻断；
2. 未完整接受的 P1；
3. 发布关键证据缺口；
4. 关键任务、内容真实性、无障碍、响应式、性能与回退；
5. 测试、监测和回滚。

### Track B — Elevate

基于品牌和内容，而不是参考站外观：

1. 写一句不可互换的体验命题；
2. 选择一个适合任务的叙事原型；
3. 建立排版、网格、色彩、媒体和动效职责；
4. 设计一个可解释、可降级的签名机制；
5. 覆盖移动、键盘、reduced-motion、加载、空、错、成功状态；
6. 做相似性审查，删除模板化借用。

不得在 Stabilize 的 P0/P1 未受控时用沉浸效果掩盖问题。

## 8. 分阶段执行计划

使用项目阶段，不假装知道真实日历：

| 阶段 | 目标 | 任务 | Owner | 依赖 | 退出条件 |
|---|---|---|---|---|---|
| Phase 0：Contain | 阻断扩散 | 冻结版本、降级危险功能、修 P0 |  |  | 所有 P0 PASS |
| Phase 1：Stabilize | 可发布基础 | 修/接受 P1、补关键证据 |  |  | 决定至少可达 CONDITIONAL-GO |
| Phase 2：Systemize | 系统一致 | tokens、组件、内容与状态 |  |  | 关键模板回归通过 |
| Phase 3：Elevate | 提升竞争力 | 概念、叙事、签名机制、精修 |  |  | 独立复审完成 |
| Phase 4：Prove | 生产验证 | 字段监测、回归、残余风险复核 |  |  | 最终审批记录完整 |

每个任务必须写成可交付变更，不使用“优化视觉”“增强体验”“提升高级感”之类无法验收的描述。

## 9. 验收、复测与回归

每个修复批次记录：

| 项目 | Baseline | Change | 同环境复测 | 回归范围 | 结果 | 决定 |
|---|---|---|---|---|---|---|
|  |  |  |  |  | KEEP / REVERT / ITERATE |  |

最低要求：

- 同一版本、设备、网络和工具条件；
- 修复项与关键任务都复测；
- 报告绝对值和差值，不只写“改善”；
- 记录副作用和新未知；
- 重新运行评分器，不手工抬分；
- 至少一次 baseline → change → retest → regression 闭环后才可宣称优化有效。

## 11. 来源分层

分别列出：

1. `OFFICIAL-CURRENT`：当前官方规则；
2. `OFFICIAL-LEGACY`：仍可访问但可能过时的官方材料；
3. `EXTERNAL-STANDARD`：W3C、web.dev 等规范；
4. `PROJECT-EVIDENCE`：本项目实测/观察/提供材料；
5. `HEURISTIC`：内部模型或项目假设；
6. `UNKNOWN/CONFLICT`：缺失或冲突。

不要把案例观察写成官方规则，也不要把内部整改目标写成行业标准。
