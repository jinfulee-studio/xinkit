## 1. 主评分公式

Awwwards 官方主模型：

`Overall = 0.40D + 0.30U + 0.20Cr + 0.10Ct`

- D = Design
- U = Usability
- Cr = Creativity
- Ct = Content

四维均为 0–10。最终报告可同时显示 `/10` 与 `/100`，但不得改权重。每维先按本文件子项加权，再由多人中位数聚合。

## 2. 通用锚点

| 分数 | 可观察锚点 |
|---:|---|
| 0 | 缺失、不可用、欺骗或造成严重伤害 |
| 1–2 | 多个核心失败；设计意图无法抵消实际阻断 |
| 3–4 | 局部可用但系统性薄弱、不一致或明显低于同类基线 |
| 5 | 基本完成；缺少区分度、证据或细节 |
| 6 | 稳健、清楚、无大面积失败；创意或打磨有限 |
| 7 | 强且一致；有清楚概念和良好执行，仍有可见缺口 |
| 8 | 独特、成熟、跨主要场景成立；细节与回退有证据 |
| 9 | 罕见的原创性与完成度；多设备、多任务和边界状态均有强证据 |
| 10 | 领域标杆；几乎无可证实缺口，且对行业方法有新贡献 |

9–10 需要至少两个不同来源、不同证据类型和跨情境验证，同时包含 `MEASURED` 与 `OBSERVED`，置信度 ≥0.8。只看 Hero、单张截图、单一 `PROVIDED/INFERRED` 材料或单个动画时不得给 9–10；评分器会拒绝这类输入。

## 3. 四维子项

### Design

| 子项 | 维度内权重 | 检查 |
|---|---:|---|
| 概念与艺术指导 | 25% | 视觉选择是否来自品牌、内容和体验命题 |
| 层级与构图 | 25% | 扫描顺序、节奏、网格、受控张力、留白 |
| 排版/色彩/媒体 | 20% | 角色、可读性、对比、图像/视频/3D 的职责 |
| 系统一致性与状态 | 20% | tokens、组件、交互/加载/空/错/成功状态 |
| 响应式完成度 | 10% | 不是缩小桌面；多尺寸与内容压力下仍成立 |

`D = .25a + .25b + .20c + .20d + .10e`

### Usability

| 子项 | 维度内权重 | 检查 |
|---|---:|---|
| 任务与信息架构 | 25% | 用户能否理解目标并完成最短关键路径 |
| 导航与可发现性 | 20% | 位置、标签、搜索/筛选、返回与方向感 |
| 反馈、状态与恢复 | 20% | 反馈及时、错误可恢复、状态不丢失 |
| 响应式与输入方式 | 20% | 移动、触摸、键盘、缩放与不同网络 |
| 可访问性与用户控制 | 15% | 语义、焦点、对比、动效控制与替代内容 |

`U = .25a + .20b + .20c + .20d + .15e`

Accessibility 在主模型中影响 Usability，但发布门禁另行独立执行，不能被平均。

### Creativity

| 子项 | 维度内权重 | 检查 |
|---|---:|---|
| 原创概念 | 35% | 是否超越模板，且不是复制参考项目 |
| 有意义的互动 | 30% | 签名机制是否强化内容、任务或品牌隐喻 |
| 品牌专属性 | 20% | 换掉 Logo 后是否仍只能属于该品牌 |
| 媒体/技术创新 | 15% | 技术是否创造新理解而非炫技 |

`Cr = .35a + .30b + .20c + .15d`

没有 WebGL/3D 不扣分；没有概念依据的 WebGL/3D 也不加分。

### Content

| 子项 | 维度内权重 | 检查 |
|---|---:|---|
| 清晰与相关 | 30% | 是什么、给谁、为何重要、下一步 |
| 叙事与层级 | 25% | 信息揭示、章节、扫描和上下文 |
| 证据与可信度 | 25% | 案例、数据、客户、来源、声明口径 |
| 文案/媒体/本地化 | 20% | 语气、细节、字幕/替代、语言覆盖 |

`Ct = .30a + .25b + .25c + .20d`

## 4. 证据置信度

置信度不改变分数，而是说明分数可信程度。

| 置信度 | 证据条件 |
|---:|---|
| 1.0 | 可复现测量 + 代表性场景 + 独立复核 |
| 0.8 | 评审者直接检查主要场景，但覆盖仍有限 |
| 0.6 | 团队提供或只覆盖单一环境 |
| 0.4 | 截图/原型推断，或间接证据 |
| 0.2 | 极弱线索；通常应改标 UNKNOWN |
| 0.0 | UNKNOWN，不得给分 |

证据标签同时构成硬上限：`MEASURED ≤1.0`、`OBSERVED ≤0.8`、`PROVIDED ≤0.6`、`INFERRED ≤0.4`。一个子项使用多条支撑证据时采用最弱支撑证据上限；`UNKNOWN/CONFLICT` 只写入限制，不能混入数值分的支撑列表。

维度置信度取支撑该维度各评审置信度的中位数。整体置信度按官方四维权重计算，但要同时列出最低维度，防止平均掩盖。

目标产物状态与实际访问方式必须分开。截图审计的交互、状态、输入与 Accessibility 子项自动为 `UNKNOWN`，其他可见项受较低置信度限制；Figma/原型也受相应能力上限。仅有单一真实评审者时整体置信度上限 0.8。

## 5. 多评审聚合

1. 各评审者先独立给四维分和置信度；
2. 每维取中位数，不取加权人情分；
3. 记录 `spread = max - min`；
4. spread >1.5 时标 `RECONCILE`；
5. 调解时只交换证据与锚点，不讨论希望达到的目标分；
6. 保留调解前分数，防止结果清洗。

记录真实 `reviewer_identity`；同一人三个隔离 pass 可以用于降低个人偏差，但仍按单一评审者限制置信度。完全相同的克隆分卡不增加独立性。若只有一个完整分数，spread 不可用，不能表述为“评审一致”。任一评审的必需子项未知时，该维度标 `INCOMPLETE` 并输出上下界，不生成伪精确总分。

## 6. Awwwards 比较线与 Developer 代理分

- `<6.5`：低于保守 HM 内部比较线；
- `≥6.5`：达到或超过保守内部比较线，但不是 HM 预测或保证；
- SOTD：无官方固定门槛，不给“通过线”；
- Developer Award：官方称只对 SOTD 项目复审，技术分高于 7 才可获得。

当前 Awwwards 仍链接的旧 Developer 指南给出历史模型：

`Dev proxy = .20 WPO + .20 Responsive + .15 Markup + .20 Semantics/SEO + .15 Animation + .10 Accessibility`

可以把它作为 `LEGACY/IN-TRANSITION` 代理分单独呈现，不能替代当前 WCAG 2.2、Core Web Vitals 与发布门禁，也不能把非 SOTD 项目称为 Developer Award 候选。

## 7. 整改优先级

P0 永远最先，不参与商业排序。其余 finding 可计算：

`Priority = Impact × Reach × Confidence ÷ Effort`

- Impact：1–5，对用户/业务/质量的影响；
- Reach：1–5，受影响任务、页面或用户范围；
- Confidence：0.4 / 0.6 / 0.8 / 1.0；
- Effort：1–5，相对工作量。

同分时先修共同根因、依赖前置和能同时改善多个维度的项目。该公式是项目启发式，不是 Awwwards 官方规则。
